# M-Ingress — External-client → node injection

**Working name:** M-Ingress (a.k.a. M16.5-Backend; sequenced after M16-Backend SHIPPED 2026-05-08)
**Product:** GraphReact (Backend) — independent of GraphReactDB ([decision 0003](decisions/0003-graphreact-bifurcates-into-backend-and-db.md))
**Status:** SHIPPED 2026-05-09 — all four phases landed. Single-message inject + request-response call + bulk NDJSON + closeout (bench `case_h_external_inject` within macOS noise band, real-binary E2E subprocess test green, [decision 0004](decisions/0004-ingress-as-substrate-primitive.md) ratified, plan-file flipped).

## Why this exists

GraphReact (Backend) is a first-class product. M16-Backend SHIPPED covered the **observability** substrate (Prometheus, OTel, JSON logs, management API GETs, ratatui CLI, per-body debug). It is NOT the complete Backend product — there was no path for an external HTTP client to push a message into an actor node's inbox. Every backend application had to BYO HTTP listener and inject-message glue, the exact asymmetry the [substrate-not-MVP rule](https://example.invalid/feedback) warns against. M-Ingress closes the gap.

Distinct from M16-DB's typed reducers against domain state. M-Ingress is **untyped (or app-typed) message injection into actor inboxes** — an actor-system primitive every backend application class needs.

## Phase plan

| Phase | Slice | Status |
|---|---|---|
| 1 | Single-message inject — `POST /v1/nodes/:id/messages` + `accepts_external` manifest gating + delivery permission check + CORS + idempotency | **SHIPPED 2026-05-09** |
| 2 | Request-response — `POST /v1/nodes/:id/call` + `correlation_id` on `Message` (WIRE_VERSION 3→4 + `INGRESS_CALL_V1` capability flag) + auto-propagation + reply registry + timeout | **SHIPPED 2026-05-09** |
| 3 | Bulk/streaming inject — `POST /v1/nodes/:id/messages/bulk` (NDJSON) + per-line idempotency + streaming ack | **SHIPPED 2026-05-09** |
| 4 | Closeout — bench, E2E subprocess test, decision 0004, plan-file flip | **SHIPPED 2026-05-09** |

## Architectural decisions

1. **Substrate-not-MVP applies in full.** All three patterns (single-inject + request-response + bulk-inject) ship together as one milestone.
2. **`.grx` grammar unchanged.** External-message permissions live in the component-returned `PermissionManifest`, mirroring `accepts` / `emits`.
3. **`SchedulerHandle::send()` is the inject substrate.** Already shipped. M-Ingress wires HTTP to it, not around it.
4. **`SnapshotRequest` enum extends in place.** New `InjectMessage` variant; existing drain pattern in `drive_handle_until` reused.
5. **Default-deny external messages.** Pre-M-Ingress, no node accepts external messages (the runtime had no path). Post-M-Ingress, a node accepts external messages ONLY for types listed in its `accepts_external` manifest field.
6. **CORS in M-Ingress, not M-Prod.** Browser is now a first-class consumer; baseline `tower-http::cors::CorsLayer` ships here. Origin allowlists / credential modes refined in M-Prod.
7. **Bearer auth stays single-shared-secret.** Per-node ACLs / multi-token deferred to M-Prod (#4-#6). Default-deny manifest gating gives ingress a defensible posture without RBAC.
8. **Correlation via `Message.correlation_id`, NOT ephemeral reply nodes** (Phase 2). Mirrors M16-Backend P10's `trace_context` propagation pattern. Auto-propagation: runtime captures inbound correlation_id; auto-attaches to the first emitted message of the call's declared `reply_type`. Component author writes `useEmit('reply', payload)` as normal. Rejected ephemeral-node alternative chosen against for zero per-call mount/unmount overhead + cleaner telemetry.

## Wire-format spec

### POST /v1/nodes/:id/messages — single-message inject

**Request:**
```http
POST /v1/nodes/sensor.temp.1/messages HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
Idempotency-Key: 7b3f8a2e-9c1d-4f8b-a3e5-2b8a1f3c6d7e

{ "type": "calibrate", "payload": { "offset": 0.5 } }
```

**Responses:**

| Status | Body | Meaning |
|---|---|---|
| `202 Accepted` | `{ "status": "accepted" }` | Message queued onto node's inbox. Manifest `accepts_external` enforcement happens at delivery; rejection surfaces in `MessageDelivered { accepted: false }` events on the live stream, NOT in this response. |
| `400 Bad Request` | (axum default) | Malformed body / missing `type` field. |
| `401 Unauthorized` | `401 unauthorized` | Bad bearer token; `WWW-Authenticate: Bearer realm="graphreact-observer"` header set. |
| `404 Not Found` | `{ "error": "node_not_found" }` | Node id did not resolve when the bridge thread checked. |
| `409 Conflict` | `{ "error": "idempotency_conflict", "key": "..." }` | Idempotency-Key matches a non-expired entry (TTL 10 min, cap 10k). |
| `503 Service Unavailable` | `scheduler bridge closed` / `scheduler bridge dropped response` | mpsc bridge full or scheduler shut down. |

**Headers:**

- `Authorization: Bearer <token>` — required (single-shared-secret model; loopback bind without `--observer-token-*` skips auth).
- `Content-Type: application/json` — required.
- `Idempotency-Key: <opaque-string>` — optional. If provided, duplicates within 10 min return 409 without crossing the bridge.

### POST /v1/nodes/:id/call — synchronous request/response (Phase 2)

**Request:**

```http
POST /v1/nodes/aggregator.zone-a/call HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{ "type": "query", "reply_type": "query_result", "payload": {"q": 1}, "timeout_ms": 30000 }
```

**Body fields:**

| Field | Required | Default | Notes |
|---|---|---|---|
| `type` | yes | — | Inbound message type. Runtime-checked against the target's `manifest.accepts_external_call[*].request_type`. |
| `reply_type` | yes | — | Expected reply type. The runtime auto-tags the FIRST outgoing emit with this `type` (in the receiving handler) with the inbound's `correlation_id`. |
| `payload` | no | `null` | Arbitrary JSON forwarded verbatim to the node's inbox. |
| `timeout_ms` | no | `30000` | Server caps at `300000` (5 min). On expiry → 504. |

**Responses:**

| Status | Body | Meaning |
|---|---|---|
| `200 OK` | `{ "reply_type": "query_result", "payload": <reply json> }` | Handler emitted a matching reply within `timeout_ms`. |
| `400 Bad Request` | (axum default) | Malformed body / missing `type` or `reply_type`. |
| `401 Unauthorized` | `401 unauthorized` | Bad bearer token. |
| `403 Forbidden` | `{ "error": "rejected_by_manifest", "reason": "..." }` | Target's `accepts_external_call` did NOT contain a matching `(request_type, reply_type)` pair. |
| `404 Not Found` | `{ "error": "node_not_found" }` | Node id did not resolve. |
| `503 Service Unavailable` | `pending_calls registry full` / `scheduler bridge closed` / `scheduler bridge dropped response` | PendingCalls cap (10k) reached OR mpsc bridge full / scheduler shut down. |
| `504 Gateway Timeout` | `{ "error": "reply_timeout", "timeout_ms": <ms> }` | `timeout_ms` elapsed before any matching reply arrived. |

**Correlation lifecycle:**

1. Handler generates a UUIDv4 `correlation_id` server-side and registers `(correlation_id → oneshot::Sender<Value>)` in the `PendingCalls` registry; if the registry is at the 10 000-entry cap, returns 503 immediately. The registration returns a `PendingCallGuard` whose `Drop` evicts the registry entry — covers HTTP-client-disconnect (axum future cancellation) so the registry never leaks on cancelled requests.
2. Handler bridges via `SnapshotRequest::InjectMessageWithReply { node_id, message_type, payload, reply_type, correlation_id, oneshot_tx }`. The drain handler (on the scheduler thread) validates node existence + the manifest's `accepts_external_call` for a matching `(request_type, reply_type)` pair. Mismatch → `RejectedByManifest`; valid → `Dispatched` + `SchedulerHandle::send_ingress_with_correlation` injects with `from = "__ingress__"`.
3. `Scheduler::deliver` consults the target's `manifest.accepts_external_call` for the matching `request_type` and captures `(correlation_id, reply_type)` per-handler-invocation (saved/restored across nested deliveries so concurrent calls don't cross-contaminate).
4. When the handler emits, `make_emit` checks the per-invocation context: if the outgoing `type` matches `reply_type` AND no prior matching emit fired (first-match-only flag), the runtime copies `correlation_id` onto the outgoing `Message` AND fires `TelemetrySink::on_call_reply { correlation_id, payload, from, reply_type }`. The reply Message also continues through the normal scheduler queue (any graph subscribers see it).
5. The `PendingCalls` registry — installed as a `MultiplexSink` consumer alongside Prometheus + ring buffer + WebSocket — implements `on_call_reply`: looks up `correlation_id`, removes the entry, and resolves the `oneshot::Sender<Value>` with the payload.
6. The HTTP handler races `oneshot::Receiver` against `tokio::time::timeout(timeout_ms)`. On reply, returns 200 + payload + `guard.disarm()` (skip Drop's redundant remove). On timeout, returns 504 + `drop(guard)` (evict).

**Auto-propagation policy:** runtime tags exactly the FIRST outgoing emit whose `type` matches `reply_type`. A handler emitting multiple downstream messages (e.g. `emit("log", ...); emit("reply", ...); emit("metric", ...)`) tags only the `"reply"`. The `tagged` flag flips after the first match so subsequent emits in the same handler invocation do NOT carry the correlation_id even if they happen to have the same type. This decouples reply identity from emit ordering.

**Decoupling reply resolution from delivery:** `on_call_reply` fires from `make_emit` BEFORE the reply Message enters the scheduler queue. This means leaf-node call handlers (no neighbors, no `direct: [...]` self-target) work correctly — the registry resolves on emit, and the reply Message's actual delivery (or non-delivery) is independent of call-flow correctness. Other graph consumers that happen to accept the reply type still see normal delivery.

### POST /v1/nodes/:id/messages/bulk — streaming NDJSON inject (Phase 3)

**Request:**

```http
POST /v1/nodes/logger.global/messages/bulk HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/x-ndjson
Content-Length: <total bytes>

{"type":"audit","payload":{"actor":"alice","action":"login"},"idempotency_key":"a1"}
{"type":"audit","payload":{"actor":"bob","action":"logout"},"idempotency_key":"a2"}
{"type":"audit","payload":{"actor":"carol","action":"upload"},"idempotency_key":"a3"}
```

**Per-line shape:** each NDJSON line is a JSON object with the fields below. Trailing `\n` between lines; `\r\n` is also tolerated; blank lines are silently skipped.

| Field | Required | Notes |
|---|---|---|
| `type` | yes | Message type. Runtime-checked against the target's `manifest.accepts_external` (single-shot allowlist — same gate Phase 1 uses). |
| `payload` | no (default `null`) | Arbitrary JSON forwarded verbatim. |
| `idempotency_key` | no | Per-line opaque dedup key. Same 10-min TTL + 10k-entry-cap `IdempotencyCache` shared with Phase 1. Per-line because the `Idempotency-Key` HTTP header is single-valued and doesn't apply to a multi-line request. |

**Response:** 200 OK + `Transfer-Encoding: chunked` + `Content-Type: application/x-ndjson`. Body is a stream of per-line response records:

```ndjson
{"line":0,"result":"accepted"}
{"line":1,"result":"accepted"}
{"line":2,"result":"rejected_by_manifest"}
{"line":3,"result":"idempotency_conflict"}
{"line":4,"result":"bad_json"}
```

**Per-line `result` strings:**

| `result` | Meaning |
|---|---|
| `accepted` | Manifest gate passed; message dispatched via `SchedulerHandle::send_ingress`. |
| `node_not_found` | Target node id did not resolve at dispatch time. |
| `rejected_by_manifest` | Target's `manifest.accepts_external` does not contain this `type`. Distinct from Phase 1's single-shot path (which defers manifest gating to delivery + observes via telemetry stream); bulk hoists the gate to drain so streaming clients see the rejection inline. |
| `bad_json` | Line failed JSON parsing. The bridge is NOT invoked for malformed lines (parser-side rejection). |
| `idempotency_conflict` | The line's `idempotency_key` matched a non-expired entry in the shared `IdempotencyCache`. Bridge NOT invoked. |
| `backpressure_503` | mpsc bridge full at this line. The handler emits this terminator AND closes the response stream — clients should retry from line N+1 after backoff. |
| `bridge_dropped` | The drain side dropped its `oneshot::Sender` before responding (typically scheduler shutdown). Stream continues for subsequent lines but operators should investigate. |
| `exceeded_line_cap` | The `GRX_INGRESS_BULK_LINE_CAP` was reached (default 10 000). Final terminator line; stream closes. |
| `line_too_large` | The line's bytes exceeded `BULK_MAX_LINE_BYTES = 1 MiB`. The handler resyncs to the next `\n` and continues processing subsequent lines. |

**Error responses (status ≠ 200):**

| Status | Body | Meaning |
|---|---|---|
| `401 Unauthorized` | `401 unauthorized` | Bad bearer (same auth as the rest of the management API). |
| `413 Payload Too Large` | `{ "error": "body_too_large", "max_bytes": <n> }` | Pre-flight `Content-Length` cap (`BULK_MAX_BODY_BYTES = DEFAULT_BULK_LINE_CAP × BULK_MAX_LINE_BYTES`) exceeded. Body never reaches the streaming handler. |

**Configurable cap:** `GRX_INGRESS_BULK_LINE_CAP` env var. Default 10 000 lines; configurable per-deployment. The 200 OK status is sent at handler entry (after the pre-flight `Content-Length` check), so even a partial-failure run that hits the cap mid-body returns 200 + the streamed `exceeded_line_cap` line — the per-line response shape is the source-of-truth for client decision-making.

**Auth + manifest semantics:**

- Same bearer-token gate as the rest of the management API (`Authorization: Bearer ...`).
- Each line is independently manifest-gated against the target's `accepts_external` allowlist. Mixed-disposition requests are common and explicitly supported (some lines accepted, some rejected).
- The `IdempotencyCache` is shared with Phase 1's single-shot path — a key used in single-shot also dedupes against bulk and vice versa. Operators wanting independent cache pools should deploy separate daemons.

### Cluster wire-format propagation (Phase 2)

`Message.correlation_id` propagates over the cluster wire format at `WIRE_VERSION = 4` (bumped from 3 with the M-Ingress phase 2 ship). The bump is a hard floor (`MIN_SUPPORTED_VERSION = 4`); v3 peers cannot interop with v4 peers, matching M16-Backend Phase 10's `WIRE_VERSION 2 → 3` precedent. Rolling-version negotiation remains M-Prod scope.

Within v4, the `INGRESS_CALL_V1_CAPABILITY = "ingress-call-v1"` flag advertised in `Hello.capabilities` / `ChallengeAck.server_capabilities` gates correlation_id propagation on the outbound serialization side: a sender targeting a peer WITHOUT the capability strips correlation_id (sets it to `None` on `wire::Message`) before encoding, even if the local Message's value is `Some(_)`. Receivers from peers without the capability still parse the field (postcard requires it for v4 wire shape) but treat `correlation_id` from a non-cap peer as semantically inert (the peer wouldn't have a `PendingCalls` registry to resolve against).

The `grx cluster daemon` always advertises `ingress-call-v1` because the management API call endpoint ships by default; non-call workloads pay no additional cost (correlation_id stays `None` on every emit).

### PermissionManifest annotation

Component author declares external-message acceptance in the manifest object their component returns:

```javascript
function Aggregator() {
  const emit = useEmit();
  useMessage('query', (msg) => {
    emit('query_result', { answer: 42 });
  });
  return {
    accepts: ['reading'],                           // existing — node-to-node delivery
    emits: ['rollup', 'query_result'],              // existing
    accepts_external: ['calibrate'],                // M-Ingress phase 1 — HTTP injection
    accepts_external_call: [                        // M-Ingress phase 2 — HTTP call shape
      { request_type: 'query', reply_type: 'query_result' },
    ],
  };
}
```

The two acceptance lists are independent trust boundaries — `accepts_external` covers single-shot inject (`POST /v1/nodes/:id/messages`); `accepts_external_call` covers request/response (`POST /v1/nodes/:id/call`). Declaring one does NOT grant the other; nodes that want both must declare both.

**Default-deny semantics:** absent or empty `accepts_external` ⇒ node refuses every external type. The HTTP path returns 202 (queued) but `Scheduler::deliver` drops the message with `accepted: false` in the telemetry stream. Operators see the rejection via `/v1/observer/events` filtered by `?type=message_delivered` + filtering for `accepted: false`.

### CORS

Baseline `CorsLayer`:
- `Access-Control-Allow-Origin: *`
- `Access-Control-Allow-Methods: GET, POST, OPTIONS`
- `Access-Control-Allow-Headers: authorization, content-type, idempotency-key`

Loopback bind appropriate; production deploys behind a header-injecting reverse proxy provide their own per-origin policy. M-Prod refines (per-origin allowlists, credential modes).

| Phase 2 unlocks | Why |
|---|---|
| **LARQL** RPC-style query requests | `POST /v1/nodes/query-engine/call` `{type:"query", reply_type:"query_result", payload:{q:"..."}}`; handler emits `query_result` and runtime auto-routes the reply. |

| **Biological pathway sim** simulation-step control | Synchronous `step` calls against a sim-controller node return computed deltas in the reply payload. |

| Phase 3 unlocks | Why |
|---|---|
| **NewsCaster** firehose ingestion | Streaming player events (thousands/sec) via `POST /v1/nodes/event-ingestor/messages/bulk` with one event per line; per-line idempotency keys deduplicate retries. |
| **ComplyFlow** audit-log ingestion at scale | Compliance dashboards POST audit batches as NDJSON; per-line manifest gating + `bad_json` surfacing lets the dashboard detect mid-stream failures inline. |
| **Reputation systems** trust-event ingestion | High-throughput trust deltas batched into NDJSON; bridge backpressure surfaces as `backpressure_503` terminator + retry-from-line-N+1 client semantics. |
| **All ingestion-shaped backend apps** | Substrate-not-MVP: any application class with high-throughput ingest needs gets it without per-app HTTP scaffolding. |

## What's NOT in M-Ingress

- ❌ Multi-token RBAC / per-node ACLs / JWT claims — M-Prod #4-#6
- ❌ Per-IP / per-token rate limiting — M-Prod #6 (`tower_governor`)
- ❌ Origin allowlists / credential modes for CORS — M-Prod
- ❌ TLS cert rotation under SIGHUP — M-Prod #7
- ❌ Streaming subscriptions for replies — already shipped via SSE/WS in M16-Backend P7
- ❌ File uploads via `multipart/form-data`
- ❌ gRPC transport — wrong shape for browser consumers
- ❌ Typed reducers against domain state — M16-DB territory
- ❌ `.grx` syntax extensions — manifest stays component-owned

## Visualizer-side companion (sketched; future work)

When M-Ingress ships, a downstream visualizer-side companion library — e.g. `@graphreact/client-react` — gains a small set of hooks built atop a new `post<TIn, TOut>` method on the existing `http.ts` client surface. The visualizer companion is **NOT** in M-Ingress milestone scope (decision 0002 — backend-only — keeps the runtime and frontends separate); it's documented here so the implementation belongs to a future visualizer-side phase that can pin against the `/v1/` protocol.

| Hook | Powers | Notes |
|---|---|---|
| `useNodeInject(nodeId, opts?)` | `POST /v1/nodes/:id/messages` | Returns `(messageType, payload) => Promise<InjectResult>` powered by TanStack Query `useMutation`. Surfaces `Idempotency-Key` via opts. |
| `useNodeCall(nodeId, opts?)` | `POST /v1/nodes/:id/call` | Returns `(messageType, replyType, payload, opts?) => Promise<TOut>` powered by `useMutation` + 504 timeout handling. The `replyType` parameter shape mirrors the manifest's `accepts_external_call[*].reply_type`. |
| `useNodeBulkInject(nodeId, opts?)` | `POST /v1/nodes/:id/messages/bulk` | Streaming NDJSON consumer with per-line ack callback. Surfaces `backpressure_503` + `exceeded_line_cap` terminator dispositions to the caller. |

A new visualizer-side decision doc would document the API split (inject vs call vs bulk) + its M-Ingress runtime origin. The `/v1/` paths + per-line response shapes + correlation_id semantics are the contract; companion clients pin against this contract so they don't drift.
